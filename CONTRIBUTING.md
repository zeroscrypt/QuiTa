# Участие в разработке QuiTa

Спасибо за интерес к QuiTa! Этот документ описывает, как начать участвовать в разработке.

## Как выпустить релиз

1. Слить изменения в `main` с понятными типами коммитов: `fix:` и `feat:`
   попадают в релиз, `docs:`, `chore:`, `test:` и `ci:` — нет.
2. Release Please откроет pull request вида `chore(main): release v1.1.1`
   с подъёмом версии и changelog.
3. Когда CI станет зелёным, workflow сольёт этот PR сам. Если проверка красная
   или `main` уехал вперёд — релиз ждёт человека, и это нормально.

Релиз по-прежнему идёт через pull request: версия и список изменений видны в
истории и могут быть проверены человеком, но кнопку «слить» нажимает
робот — только после зелёной проверки.


## Требования

- **Node.js** 22+
- **pnpm** 12+
- **Rust** stable (1.99+)
- **Linux**: `libwebkit2gtk-4.1-dev`, `libappindicator3-dev`, `librsvg2-dev`, `patchelf`

## Начало работы

### 1. Клонирование репозитория

```bash
git clone https://github.com/zeroscrypt/QuiTa.git
cd QuiTa
```

### 2. Установка зависимостей

```bash
pnpm install
```

### 3. Запуск в режиме разработки

```bash
pnpm tauri dev
```

## Стиль кода

### TypeScript / Svelte

- **Строгий TypeScript** — `noUnusedLocals`, `noUnusedParameters`
- **Svelte 5 runes** — `$state`, `$derived`, `$effect`
- **Именование** — camelCase для переменных и функций, PascalCase для компонентов и типов
- **Комментарии** — только для сложной логики, код должен самодокументироваться

### Rust

- **Clippy** — все предупреждения должны быть устранены (`-D warnings`)
- **Форматирование** — `cargo fmt`
- **Именование** — snake_case для функций и переменных, PascalCase для типов
- **Комментарии** — документация для публичных функций и сложной логики
- **Транзакции** — все операции записи в транзакциях
- **Параметризованные запросы** — все SQL-запросы с параметрами

## Правила коммитов

Формат сообщений коммитов:

```
<тип>: <описание>

[тело]
```

### Типы

Релизы собирает [Release Please](https://github.com/googleapis/release-please),
и тип коммита решает, попадёт изменение в релиз или нет:

| Тип | Что означает | Релиз |
|-----|-------------|--------|
| `feat` | новая функциональность | minor, **релиз** |
| `fix` | исправление ошибки | patch, **релиз** |
| `perf`, `refactor` | качество и структура | patch, **релиз** |
| `docs` | документация | без релиза |
| `style`, `test` | оформление и тесты | без релиза |
| `chore`, `ci` | рутина, сборка, пайплайн | без релиза |

Тип можно уточнить областью: `feat(ui): шторм-ввод для подзадач`.
Ломающее изменение — `feat!:` или строка `BREAKING CHANGE:` в теле.

### Язык сообщений

Типы и области остаются английскими — это формат, который читает
автоматика. Всё остальное по-русски, и не по недосмотру: Release Please
берёт текст сообщения в changelog как есть, поэтому по-русски коммиты дают
по-русский changelog, а он читается рядом с README и документацией.

Смешивать не стоит. Половина release notes на одном языке, половина на другом
выглядит не как два релиза одного проекта, а как два разных.

Служебные префиксы при этом обязательны: без них изменение не попадёт ни в
один changelog, даже если текст написан идеально.

**Почему это важно.** Без явных типов Release Please выпускает релиз на любой
коммит. С ними правка README или починка workflow не заставляют пользователей
обновляться — а именно это и происходило на старте: четыре слияния подряд дали
четыре релиза, три из которых сломались о собственный пайплайн.

### Примеры

```
feat(ui): шторм-ввод для подзадач

fix(trash): подтверждение очистки всей корзины

docs: обновить README

ci: починить сборку на Windows
```

## Как добавлять миграции

1. Создайте новую миграцию в `src-tauri/src/db/migrations.rs`
2. Увеличьте номер версии
3. Добавьте SQL в константу `MIGRATIONS`
4. Миграция применится автоматически при следующем запуске

### Пример

```rust
const MIGRATIONS: &[Migration] = &[
    Migration {
        version: 1,
        name: "create_tasks_and_settings",
        sql: r#"..."#,
    },
    Migration {
        version: 2,
        name: "add_tags",
        sql: r#"
            CREATE TABLE IF NOT EXISTS tags (
                id TEXT PRIMARY KEY,
                name TEXT NOT NULL
            );
        "#,
    },
];
```

### Правила миграций

- **Не изменять существующие миграции** — только добавлять новые
- **Идемпотентность** — используйте `IF NOT EXISTS`
- **Обратная совместимость** — старые версии приложения должны работать с новой схемой (если возможно)

## Как добавлять тесты

### Rust

- Unit-тесты — в том же файле, в `mod tests`
- Интеграционные тесты — в `src-tauri/tests/integration_tests.rs`
- Используйте `open_test_db()` для in-memory базы данных

### TypeScript

- Тесты — в `tests/` директории
- Используйте vitest
- Тестируйте чистые функции из `src/domain/`

## Процесс отправки изменений

1. Создайте ветку от `main`
2. Внесите изменения
3. Убедитесь, что все проверки проходят
4. Создайте pull request
5. Опишите изменения в описании PR

## Код-ревью

- Все изменения проходят код-ревью
- Ревьюеры проверяют соответствие стилю, тесты, документацию
- Вопросы и предложения приветствуются

## Сообщение об ошибках

При сообщении об ошибке укажите:
- Версию приложения
- Операционную систему
- Шаги для воспроизведения
- Ожидаемое и фактическое поведение
- Логи (если есть)
