# Правила задач и подзадач

Документ описывает правила работы с задачами и подзадачами, реализованные в `src-tauri/src/domain/rules.rs` (функция `compute_toggle_plan`) и в триггерах базы данных.

## Иерархия задач

### Один уровень вложенности

Подзадачи могут быть только у корневых задач. Подзадачи подзадач не допускаются.

**Применение:**
- **Доменная логика**: `repository::create_task` проверяет `parent.is_root()` и возвращает `TaskError::ThirdLevelForbidden`
- **Триггер БД**: `task_no_third_level_insert` и `task_no_third_level_update` блокируют INSERT и UPDATE с третьим уровнем

### Завершённый родитель принимает подзадачи

Подзадачу добавить к завершённой задаче можно: строка тогда читается как
«частично выполнено» — задача закрыта, а работа под ней осталась.

**Применение:**
- `repository::create_task` проверяет только `parent.is_root()` и отклоняет
  лишь третий уровень вложенности (`TaskError::ThirdLevelForbidden`)
- UI: `canHaveSubtasks` в `src/domain/taskRules.ts` проверяет только
  `task.parentId === null`
- Тест: `completed_parent_can_receive_new_subtasks`

## Завершение задач

### Завершение родителя завершает подзадачи

При завершении корневой задачи все её незавершённые подзадачи завершаются автоматически. Это поведение каскада (`cascade_complete`, по умолчанию включён): при выключенном каскаде галочка родителя меняет только его самого.

**Механизм:**
1. Генерируется `completion_event_id` (UUID)
2. Родителю записывается `completion_event_id`
3. Каждой автоматически завершённой подзадаче записывается `auto_completed_by` = `completion_event_id`
4. Все изменения выполняются в одной транзакции

### Ручные завершения подзадач не затрагиваются

Если подзадача была завершена вручную (не через родителя), она остаётся завершённой при завершении родителя.

**Критерий:**
- `auto_completed_by IS NULL` — ручное завершение
- `auto_completed_by = completion_event_id` — автоматическое завершение

### Повторное открытие родителя

При повторном открытии (снятии отметки завершения) корневой задачи восстанавливаются только подзадачи, которые были автоматически завершены этим родителем.

**Критерий восстановления:**
- Подзадача завершена (`completed_at IS NOT NULL`)
- Подзадача имеет `auto_completed_by` = `completion_event_id` родителя

Подзадачи, завершённые вручную, остаются завершёнными.

## Взаимодействие с родителем

### Подзадача никогда не трогает родителя

Ни завершение, ни открытие подзадачи не меняет состояние её родителя — ни в
той же транзакции, ни как-либо иначе.

**Обоснование:** закрытая задача с открытыми подзадачами — это обычное
состояние «частично выполнено», а не ошибка. Родитель закрыт потому, что его
закрыл пользователь; молча открывать его обратно, когда снята галочка с
подзадачи, значит отменять его действие без спроса.

Так это выглядит на практике:

| Действие | Родитель | Подзадачи | Что видит пользователь |
|----------|----------|-----------|-------------------------|
| Закрыть корневую (каскад вкл.) | закрыта | закрыты каскадом | обычная закрытая задача |
| Снять галочку с подзадачи | **остаётся закрытой** | эта открыта | частично выполнено: прочерк оранжевым |
| Открыть корневую | открыта | каскад открывает только свои | всё как было |

### «Частично выполнено» — полноценное состояние

Снятие галочки с подзадачи не меняет данные родителя: он остаётся закрытым, но
получает обычный вид «частично выполнено», тот же, что возникает при
выключенном каскаде. Счётчик подзадач и прогресс пересчитываются, потому что
подзадача снова открыта.

Подзадача при этом теряет отметку `auto_completed_by`: она больше не
принадлежит событию каскада. Поэтому последующее открытие родителя не
закроет её обратно — открытое пользователем остаётся открытым.

## Удаление и восстановление

### Каскадное мягкое удаление

При удалении корневой задачи все её подзадачи также удаляются атомарно (в одной транзакции).

**Особенности:**
- Удаление мягкое (`deleted_at` устанавливается в текущий timestamp)
- Возвращается список удалённых задач (родитель первым)

### Восстановление возвращает всё, что лежит в корзине

Восстановление корневой задачи возвращает и её подзадачи, потому что иначе они
остались бы в корзине навсегда — видимые, но недоступные.

**Правила:**
- Восстановление корневой задачи возвращает всех её мягко удалённых подзадач
- Подзадача, восстановленная отдельно, когда её родитель ещё в корзине,
  становится **корневой** (`parent_id` сбрасывается в `NULL`)
- Корзина показывает ровно то, что в ней лежит: и корневые задачи, и подзадачи

Список корзины ограничен 200 задачами — это граница отрисовки, а не границы
данных. Всё, что не влезло, догружается кнопкой «Показать ещё», иначе задача
за пределами первой страницы осталась бы недостижимой: восстановить её нечем,
нет строки, у которой есть кнопка.

Число в шапке и в подтверждении очистки — настоящее, а не длина загруженного
списка. Показывать длину окна рядом с кнопкой «удалить всё» значило, что
человек соглашался удалить 200 задач, а исчезали все 300.

**Обоснование:** правило «родитель должен быть восстановлен раньше» делало данные
недостижимыми — подзадача оставалась удалённой, но восстановить её было нельзя.
Приоритет отдан обратному: всё, что попало в корзину, обязано быть
восстановимым. Корневая задача при этом не остаётся с незавершёнными подзадачами,
потому что подзадача просто меняет уровень.

### Сортировка при восстановлении

Восстановленная корневая задача встаёт в список согласно своему `sort_order`.

## Ввод задач (шторм)

### Один ритм для обоих полей

Поле корневых задач и поле подзадач — это одно и то же поле с точки зрения
пользователя. Оба реализуют один и тот же набор правил (`src/lib/capture.ts`),
иначе пришлось бы запоминать два разных порядка действий.

| Событие | Поле корневых задач | Поле подзадач |
|---------|--------------------|---------------|
| `Enter` | создать, очистить, **остаться в фокусе** | создать, очистить, **остаться в фокусе** |
| `Esc` | очистить набранное | закрыть поле, ничего не создав |
| Клик мимо поля | неприменимо (поле всегда на виду) | сохранить набранное и закрыть |
| Поле пустое | ничего не происходит | закрывается |

**Обоснование:** запись должна быть быстрее мысли. Всё, что закрывает поле или
уводит фокус, превращает набор задач в диалог с кнопкой.

### Защита от повторного создания

Пока сохранение выполняется, следующий `Enter` игнорируется: удержание клавиши
не должно создавать дубликаты.

### Подсказка под полем подзадач

Пока поле подзадач открыто, под ним показано: `Enter` — добавить ещё,
`Esc` — закрыть. Без неё шторм неотличим от старого поведения, при котором
`Enter` закрывал поле.

## Перетаскивание и порядок

### Три зоны строки

Строка задачи разделена по вертикали на три зоны:

| Зона | Действие |
|------|----------|
| верхняя четверть | вставить перед задачей |
| средняя половина | сделать подзадачей этой задачи |
| нижняя четверть | вставить после задачи |

### Позиция «после последней задачи» — полноценная

Положение указателя под последней строкой списка (включая пустое место под
списком) означает «вставить в конец». Это единственный способ поставить задачу
последней, поэтому оно должно быть и достижимым, и видимым:

- строка под последней задачей рисуется как обычная линия вставки;
- попадание под последнюю строку даёт `dropIndex = длина списка`.

**Почему так:** раньше позиция определялась через `elementFromPoint(...).closest(...)`,
а линия вставки — соседний элемент, а не сама строка. Указатель над линией
не находил ни одной строки, и сброс в конец был недостижим: пользователь видел
линию только *над* строками и всегда попадал на предпоследнюю позицию.

### Порядок определяется геометрией, а не DOM-поиском

Строка под указателем определяется сравнением координат с прямоугольниками
всех строк. Это не зависит от того, над каким элементом оказался курсор:
строки, отступы `<li>`, линия вставки или пустое место под списком.

### Перенос в группу подзадач

Задача, перетащенная на строку подзадачи, встаёт на **показанную позицию**, в
том числе в конец группы (раньше она всегда дописывалась в конец независимо от
позиции, что противоречило нарисованной линии).

Если у переносимой задачи есть свои подзадачи, они расплющиваются и входят в
ту же группу — весь состав группы записывается заново, чтобы порядок не
получился противоречивым.

## Сроки

### Срок родителя не влияет на подзадачи

Установка срока для корневой задачи не изменяет сроки подзадач. Каждая задача имеет свой независимый срок.

## Примеры сценариев

### Сценарий 1: Завершение родителя с подзадачами

```
Родитель (активный)
├── Подзадача А (активная)
└── Подзадача B (завершена вручную)

Действие: завершить родителя
Результат:
- Родитель: завершён, completion_event_id = event-1
- Подзадача А: завершена автоматически, auto_completed_by = event-1
- Подзадача B: остаётся завершённой, auto_completed_by = NULL
```

### Сценарий 2: Повторное открытие родителя

```
Родитель (завершён, completion_event_id = event-1)
├── Подзадача А (завершена, auto_completed_by = event-1)
└── Подзадача B (завершена вручную, auto_completed_by = NULL)

Действие: открыть родителя
Результат:
- Родитель: активен, completion_event_id = NULL
- Подзадача А: активна (восстановлена)
- Подзадача B: остаётся завершённой
```

### Сценарий 3: Открытие подзадачи при завершённом родителе

```
Родитель (завершён)
└── Подзадача (завершена, auto_completed_by = event-1)

Действие: открыть подзадачу
Результат:
- Подзадача: активна, auto_completed_by очищен
- Родитель: остаётся завершённым, состояние «частично выполнено»
```

## Техническая реализация

### Чистая функция `compute_toggle_plan`

Функция принимает целевую задачу, список её подзадач и признак каскада и возвращает `TogglePlan` — план изменений без обращения к базе данных.

```rust
pub struct TogglePlan {
    pub target_id: String,
    pub complete: bool,
    pub completion_event_id: Option<String>,
    pub children_to_complete: Vec<String>,
    pub children_to_reopen: Vec<String>,
}
```

Родителя в плане нет: подзадача никогда не меняет состояние родителя.

### Применение плана

Функция `apply_toggle_plan` в `repository.rs` применяет план к базе данных в одной транзакции.

### Триггеры базы данных

Два триггера обеспечивают ограничение одного уровня вложенности на уровне БД:
- `task_no_third_level_insert` — BEFORE INSERT
- `task_no_third_level_update` — BEFORE UPDATE OF parent_id
