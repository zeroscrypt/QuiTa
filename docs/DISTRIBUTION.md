# Дистрибуция QuiTa

Как собрать релиз, чем он подписан и почему ключ не лежит в репозитории.

## Как выходит релиз

Версией, changelog и тегами занимается **Release Please** — стандартное
решение от Google.

```text
коммиты в main  →  PR «chore(main): release v1.0.5»
                      ↓ человек смотрит и сливает
                  тег + GitHub Release
                      ↓ build.yml собирает установщики
```

Релиз — это **pull request**, а не автоматический пуш: подъём версии и
changelog проходят обычное ревью, как любой другой код.

### Что попадает в релиз, а что нет

Решение принимает тип коммита:

| Тип | Повышение | Релиз |
|-----|-----------|--------|
| `fix:` | patch | да |
| `feat:` | minor | да |
| `perf:`, `refactor:` | patch | да |
| `docs:`, `test:`, `chore:`, `ci:` | ничего | **нет** |

Правка README или починка workflow не заставляют пользователей обновляться —
именно это и ломало предыдущую схему, где каждое слияние порождало релиз.

Формат сообщения: `fix: короткое описание`, можно со scope — `feat(ui): шторм-ввод`.
Breaking change — `feat!:` или `BREAKING CHANGE:` в теле сообщения.

### Почему сборка отдельным workflow

Release Please создаёт тег `GITHUB_TOKEN` репозитория, а GitHub **не запускает
workflow от действий, сделанных этим же токеном** — защита от рекурсии. Поэтому
`release.yml` после создания релиза явно вызывает `build.yml` через
`workflow_dispatch`: это единственное исключение из правила.

Пересобрать релиз вручную:

```bash
gh workflow run build.yml --ref main -f tag=v1.0.4
```

### Где живёт номер версии

| Файл | Чем обновляется |
|------|-----------------|
| `package.json` | Release Please, стратегия `node` |
| `src-tauri/Cargo.toml` | `extra-files`, `jsonpath: $.version` |
| `src-tauri/tauri.conf.json` | `extra-files`, `jsonpath: $.version` |
| `.release-please-manifest.json` | текущая выпущенная версия |

Расхождение между ними ломает обновление молча: приложение сравнивает версию
бинаря с манифестом релиза и просто перестаёт показывать плашку. Поэтому перед
сборкой `build.yml` проверяет, что версия в checkout совпадает с тегом
(`scripts/bump-version.mjs --check`).

### Что попадает в релиз

| Платформа | Файлы |
|-----------|-------|
| macOS | `QuiTa_<версия>_aarch64.dmg`, `QuiTa_<версия>_x64.dmg` |
| Windows | `QuiTa_<версия>_x64-setup.exe`, `QuiTa_<версия>_x64_en-US.msi` |
| Linux | `QuiTa_<версия>_amd64.AppImage`, `QuiTa_<версия>_amd64.deb` |

Плюс `SHA256SUMS` и служебные файлы обновления (`latest.json`, `.sig`,
`*.app.tar.gz`) — их не видно в списке релизов, они лежат среди ассетов.

## Проверка целостности

Скрипты установки не доверяют ни одной сумме, полученной из того же места, что и
файл. Порядок такой:

1. `install.sh` / `install.ps1` скачивают `SHA256SUMS` с GitHub.
2. Находят в списке имя нужного файла.
3. Считают SHA-256 **после** скачивания и сверяют.
4. Только после совпадения распаковывают и запускают установку.

Отключается переменной окружения `QUITA_SKIP_CHECKSUM=1`, но в скрипте есть
отдельная проверка, которая предупреждает о потере защиты.

## Подпись обновлений

Приложение проверяет новую версию сама — зелёной плашкой над вкладками. Чтобы
эта проверка что-то значила, обновление должно быть подписано.

### Что где лежит

| Ключ | Где | Виден пользователям |
|------|-----|---------------------|
| Публичный | `src-tauri/tauri.conf.json` → `plugins.updater.pubkey` | Да, и это нормально |
| Приватный | секрет GitHub `TAURI_SIGNING_PRIVATE_KEY` | Нет, и не должен |

Публичный ключ попадает в бинарь — им проверяется подпись скачанного обновления.
Приватный нужен только в момент сборки релиза и в готовом приложении его нет
(это проверяется: `grep "rsign encrypted secret key" QuiTa.app` не находит
ничего).

### Почему `createUpdaterArtifacts` только в CI

Артефакты для обновлений включаются флагом в самом workflow, а не в
`tauri.conf.json`. Причина практическая: с этим флагом `pnpm tauri build`
**падает** на машине без ключа подписи, а contributor должен иметь возможность
собрать проект, ничего не настраивая.

Если секрет не задан, релиз всё равно соберётся — но без `latest.json`, и
обновления в приложении просто не появятся. Workflow в этом случае печатает
предупреждение.

### Что будет, если потерять приватный ключ

Новые релизы нельзя будет раздать автообновлением: подпись не сойдётся, и
установленные копии QuiTa молча перестанут обновляться. Публичный ключ менять
нельзя — это ломает проверку у всех, кто уже установил приложение.

Выход в таком случае один: публиковать новые версии вручную через GitHub
Releases и предлагать скачать файл.

## Установка из репозитория

`scripts/install.sh` (macOS, Linux) и `scripts/install.ps1` (Windows) лежат в
репозитории и не меняются вместе с релизом: они всегда тянут `latest` из API
GitHub.

```bash
curl -fsSL https://raw.githubusercontent.com/zeroscrypt/QuiTa/main/scripts/install.sh | bash
```

Полезные переменные окружения:

| Переменная | Что делает |
|------------|-----------|
| `QUITA_VERSION` | Установить конкретную версию вместо последней |
| `QUITA_INSTALL_DIR` | Каталог установки |
| `QUITA_REPO` | Другой репозиторий (для форков) |

### Что проверяется до установки

Обе версии скрипта сначала смотрят на машину и только потом что-то качают —
иначе пользователь получает файл, который невозможно поставить:

| Проверка | macOS / Linux | Windows |
|----------|---------------|---------|
| Уже установлена та же версия | выход без установки | выход без установки |
| Установлена более новая версия | отказ понижать версию | отказ понижать версию |
| Приложение ещё запущено | требование закрыть | требование закрыть |
| Нужны права администратора | не нужны | обязательны, иначе `1603` |

Приложение живёт в трее, поэтому закрытое окно не значит остановленный
процесс: замена запущенного приложения оставила бы старое в памяти, работающее
с файлами, которых на диске уже нет.

### Когда установка всё-таки упала

Windows сворачивает разные причины в один код, поэтому после неудачи скрипт
печатает расшифровку кода и оставляет полный лог установщика, печатая из него
блок вокруг `Return value 3` — там установщик пишет, что именно не смог.

Частые коды:

| Код | Что означает |
|-----|--------------|
| `1603` | установка не удалась; причина — в логе |
| `1618` | уже идёт другая установка |
| `1620` | повреждённый MSI |
| `1638` | установлена другая версия |
| `3010` | установлено, Windows просит перезагрузиться |

Лог лежит в `%TEMP%\quita-install-*.log` и переживает установку намеренно:
удалять его в `finally` означало бы показывать пользователю путь к файлу,
которого уже нет.

## Нотаризация macOS

Пока не настроена: приложение не подписано Developer ID и не нотарифицировано,
поэтому первый запуск на чужом Mac требует подтверждения в системных настройках.

Как только появится подпись, порядок сборки меняется: собрать `.app` → подписать
→ notarize → запечатать в `.dmg`. Именно тогда замена бинаря изнутри станет
невозможной и обновление должно идти только через проверку подписи.

Описание шагов и нужные секреты — в `.github/workflows/release.yml`, в секции
`tauri-action`.

## Чек-лист релиза

- [ ] Версия поднята в `package.json`, `Cargo.toml`, `tauri.conf.json`
- [ ] `cargo audit` проходит без ошибок
- [ ] `pnpm check`, `pnpm test`, `cargo test`, `cargo clippy` зелёные
- [ ] README и `docs/` не содержат устаревших чисел и правил
- [ ] Секрет `TAURI_SIGNING_PRIVATE_KEY` настроен
- [ ] Тег `vX.Y.Z` создан и отправлен
- [ ] Релиз появился в GitHub и содержит `SHA256SUMS`
- [ ] Приложение на старой версии показывает зелёную плашку обновления
