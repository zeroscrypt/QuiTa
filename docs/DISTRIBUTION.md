# Дистрибуция QuiTa

Как собрать релиз, чем он подписан и почему ключ не лежит в репозитории.

## Как выходит релиз

Версией, changelog и тегами занимается **Release Please** — стандартное
решение от Google.

```text
коммиты в main  →  PR «chore(main): release v1.1.1»
                      ↓ CI зелёный → PR сливается автоматически
                  тег + GitHub Release
                      ↓ build.yml собирает установщики
```

Релиз — это **pull request**, а не автоматический пуш: подъём версии и
changelog остаются в истории и видны, как любое другое изменение. Кнопку
«слить» нажимает workflow — только после того, как позеленела проверка.

### Кто сливает релизный PR

Только тот PR, который открыл сам Release Please, — его номер берётся из
выхода действия, а не ищется по названию.

Раньше номер находился поиском по префиксу `chore(main): release`. Это
выглядело безобидно, пока репозиторий был приватным, но он публичный, и
`gh pr list` выдаёт новые PR первыми. Любой желающий мог открыть PR с таким
же названием, дождаться ближайшего пуша в `main` с зелёным CI — и его код
слился бы без ревью и без обязательных проверок, а затем попал бы в релиз,
подписанный ключом обновления.

Сейчас скрипт сверяет номер с выходом Release Please, имя ветки с префиксом
`release-please--` и состояние PR. Если что-то не совпало или номер извлечь не
удалось — слияния не происходит, релиз ждёт человека. Отказ здесь дешевле
ошибочного слияния.

Слияние ждёт **две вещи**, и обе настоящие.

Первое — зелёный CI коммита в `main`: сломанный `main` не должен уезжать
пользователям.

Второе — собственные проверки релизного PR. Их требует **защита ветки**: все
шесть задач CI перечислены как обязательные, а проверки PR читаются с его
собственной головы, так что зелёный прогон в `main` — это другой коммит и не
в счёт. Тут и была вторая, невидимая поломка: Release Please открывает PR
токеном `GITHUB_TOKEN`, а GitHub держит такие прогоны как `action_required` —
задачи не планируются вовсе, проверки не появляются, и слияние заблокировано
до чужой кнопки. Никто не пришёл, и выпуск встал.

Кнопку нажимает сам workflow: задача слияния одобряет зависший прогон — но
только после трёх сверок, которые в ней уже были: номер PR пришёл из выхода
Release Please, ветка начинается с `release-please--`, PR открыт и стоит на
текущем `main`. Одобрение не стоит ничего даже в худшем случае: тот прогон
только читает код, и этот код зелёным прогоном на `main` уже собран. Если
GitHub всё же откажет, workflow печатает ссылку на прогон и ждёт человека —
как и во всех остальных случаях.

Что происходит, если слияния не случилось — во всех случаях это нормальное
состояние, а не поломка:

| Ситуация | Что делает workflow |
|----------|---------------------|
| CI красный | ждёт: сломанный `main` не должен уезжать пользователям |
| CI не закончился за час | ждёт человека |
| `main` уехал вперёд, пока PR ждал | PR устарел, Release Please обновит его, и следующий пуш слиет свежий |
| Одобрение прогона не прошло | ждёт человека, ссылка на прогон в логе |
| У релизного PR красная проверка | ждёт: непроверенный код в релиз не уезжает |

### Если релиз не создался

Метка на релизном PR — не украшение, а закладка Release Please. Слитые релизные
PR действие находит **по метке** `autorelease: pending` и меняет её на
`autorelease: tagged`, когда релиз создан. Пока метка стоит, PR считается
невыпущенным.

Отсюда ловушка: если создание релиза не удалось, метка остаётся, и **каждое
следующее срабатывание берёт тот же самый PR и падает так же** — новый выпуск
не создаётся уже никогда. Хуже того, проверка по манифесту при этом остаётся
зелёной, если тег и релиз восстановили руками. Именно так 1.2.1 заморозил
выпуски: красный `release.yml` при зелёном сторожа.

Что именно падало — проверено опытом в самом пайплайне: GitHub отвечает **403**
на создание релиза, когда у тега уже есть релиз, а запрос передаёт
`target_commitish`. Тот же вызов без этого поля даёт 422 `already_exists`, а для
свежего тега — 201. Release Please передаёт `target_commitish` всегда, и
появившийся раньше тег делает этот вызов невыполнимым.

Выпутать:

```bash
gh pr edit <номер> --remove-label "autorelease: pending" --add-label "autorelease: tagged"
```

После этого действие перестаёт видеть в PR невыпущенный релиз и идёт дальше —
открывает новый релизный PR на свежие `feat`/`fix`. По той же причине, если
релиз приходится восстанавливать руками, метку на его PR надо поменять
самому: тег, поставленный человеком, Release Please уже не выпустит.

Задача `audit-release` проверяет обе половины обещания «каждая слитая версия
дошла до релиза»: манифест против новейшего тега и слитые релизные PR, всё ещё
носящие `autorelease: pending`, версия которых ниже манифеста. Вторая половина
и была пропущена — по одной первой 1.2.1 выглядел выпущенным.

### Что попадает в релиз, а что нет

Решение принимает тип коммита:

| Тип | Повышение | Релиз |
|-----|-----------|--------|
| `fix:` | patch | да |
| `feat:` | minor | да |
| `perf:`, `refactor:` | patch | да |
| `docs:`, `test:`, `chore:`, `ci:` | ничего | **нет** |

Правка README или починка workflow не заставляют пользователей обновляться —
именно это и ломало предыдущую схему, где каждое слияние порождало релиз.

Формат сообщения: `fix: короткое описание`, можно со scope — `feat(ui): шторм-ввод`.
Breaking change — `feat!:` или `BREAKING CHANGE:` в теле сообщения.

### Почему сборка отдельным workflow

Release Please создаёт тег `GITHUB_TOKEN` репозитория, а GitHub **не запускает
workflow от действий, сделанных этим же токеном** — защита от рекурсии. Поэтому
`release.yml` после создания релиза явно вызывает `build.yml` через
`workflow_dispatch`: это единственное исключение из правила.

### Почему сборки идут по очереди

`build.yml` объявлен в группе `concurrency: build`, поэтому сборки не идут
одновременно. Иначе каждая писала бы файлы релиза и `latest.json`, и
победила бы та, что финишировала последней, — а это способ предложить
понижение версии всем, кто на автообновлении.

Ограничение GitHub: в группе держится одна ожидающая сборка, а более старые
ожидающие отменяются. Релиз, чья сборка была вытеснена, остаётся без файлов, и
задача `report-unbuilt-releases` об этом сообщает прямо в логе. Пересобрать
такой релиз вручную:

```bash
gh workflow run build.yml --ref main -f tag=v1.1.1
```

Поэтому релиз занимает около 20 минут: если за это время выйдут ещё два,
сборки вытеснят друг друга.

### Где живёт номер версии

| Файл | Чем обновляется |
|------|-----------------|
| `package.json` | Release Please, стратегия `node` |
| `src-tauri/Cargo.toml` | `extra-files`, `jsonpath: $.version` |
| `src-tauri/tauri.conf.json` | `extra-files`, `jsonpath: $.version` |
| `.release-please-manifest.json` | текущая выпущенная версия |

Расхождение между ними ломает обновление молча: приложение сравнивает версию
бинаря с манифестом релиза и просто перестаёт показывать плашку. Поэтому перед
сборкой `build.yml` проверяет, что версия в checkout совпадает с тегом
(`scripts/bump-version.mjs --check`).

### Что попадает в релиз

| Платформа | Файлы |
|-----------|-------|
| macOS | `QuiTa_<версия>_aarch64.dmg`, `QuiTa_<версия>_x64.dmg` |
| Windows | `QuiTa_<версия>_x64-setup.exe`, `QuiTa_<версия>_x64_en-US.msi` |
| Linux | `QuiTa_<версия>_amd64.AppImage`, `QuiTa_<версия>_amd64.deb` |

Плюс `SHA256SUMS` и служебные файлы обновления (`latest.json`, `.sig`,
`*.app.tar.gz`) — их не видно в списке релизов, они лежат среди ассетов.

## Проверка целостности

Установщик проверяет две вещи, и они отвечают на разные вопросы.

### Целостность: SHA-256

`install.sh` и `install.ps1` скачивают `SHA256SUMS`, находят в списке нужный
файл, считают SHA-256 **после** скачивания и сверяют. Отключается переменной
окружения `QUITA_SKIP_CHECKSUM=1`.

### Подлинность: подпись ключом релиза

Одной суммы недостаточно: `SHA256SUMS` лежит в том же релизе, что и сам файл,
поэтому взломанный аккаунт меняет их одновременно, и сверка проходит. Подпись
публикуется под ключом, который уже вшит в каждую установленную копию
приложения, — это и есть независимый источник доверия.

Скрипты проверяют `.sig` того же файла публичным ключом из
`src-tauri/tauri.conf.json`. Требуется `minisign`:

```sh
brew install minisign      # macOS
sudo apt install minisign  # Linux
```

Если `minisign` не установлен, установка **не отменяется** — превращать
безопасную установку в заблокированную было бы хуже. Скрипт печатает
предупреждение о том, что проверена только сумма. Молча пропущенная проверка —
это не проверка; пропущенная с явным сообщением — это решение пользователя.

Расхождение подписи останавливает установку всегда, если `minisign` есть.

Цепочку можно проверить руками: подпись файла из опубликованного релиза
проверялась настоящей криптографией (ed25519 поверх BLAKE2b-512) ключом из
конфига, а не сравнением строк.

## Подпись обновлений

Приложение проверяет новую версию сама — зелёной плашкой над вкладками. Чтобы
эта проверка что-то значила, обновление должно быть подписано.

### Что где лежит

| Ключ | Где | Виден пользователям |
|------|-----|---------------------|
| Публичный | `src-tauri/tauri.conf.json` → `plugins.updater.pubkey` | Да, и это нормально |
| Приватный | секрет GitHub `TAURI_SIGNING_PRIVATE_KEY` | Нет, и не должен |

Публичный ключ попадает в бинарь — им проверяется подпись скачанного обновления.
Приватный нужен только в момент сборки релиза и в готовом приложении его нет
(это проверяется: `grep "rsign encrypted secret key" QuiTa.app` не находит
ничего).

### Почему `createUpdaterArtifacts` только в CI

Артефакты для обновлений включаются флагом в самом workflow, а не в
`tauri.conf.json`. Причина практическая: с этим флагом `pnpm tauri build`
**падает** на машине без ключа подписи, а contributor должен иметь возможность
собрать проект, ничего не настраивая.

Если секрет не задан, релиз всё равно соберётся — но без `latest.json`, и
обновления в приложении просто не появятся. Workflow в этом случае печатает
предупреждение.

### Что будет, если потерять приватный ключ

Новые релизы нельзя будет раздать автообновлением: подпись не сойдётся, и
установленные копии QuiTa молча перестанут обновляться. Публичный ключ менять
нельзя — это ломает проверку у всех, кто уже установил приложение.

Выход в таком случае один: публиковать новые версии вручную через GitHub
Releases и предлагать скачать файл.

## Установка из репозитория

`scripts/install.sh` (macOS, Linux) и `scripts/install.ps1` (Windows) лежат в
репозитории и не меняются вместе с релизом: они всегда тянут `latest` из API
GitHub.

```bash
curl -fsSL https://raw.githubusercontent.com/zeroscrypt/QuiTa/main/scripts/install.sh | bash
```

Полезные переменные окружения:

| Переменная | Что делает | `install.sh` | `install.ps1` |
|------------|-----------|--------------|---------------|
| `QUITA_VERSION` | Установить конкретную версию вместо последней | да | нет, есть параметр `-Version` |
| `QUITA_INSTALL_DIR` | Каталог установки | да | нет, на Windows свой установщик |
| `QUITA_REPO` | Другой репозиторий (для форков) | да | да |
| `QUITA_SKIP_CHECKSUM` | Всё равно поставить, если суммы нет | да | да |

Последняя переменная нужна редко: без опубликованной суммы установщик
**отказывается** ставить, потому что проверка целостности — единственное, что
отличает установку от скачивания чего попало с GitHub. Обойти это можно
только осознанно, и след остаётся в истории командной строки.

### Что проверяется до установки

Обе версии скрипта сначала смотрят на машину и только потом что-то качают —
иначе пользователь получает файл, который невозможно поставить:

| Проверка | macOS / Linux | Windows |
|----------|---------------|---------|
| Уже установлена та же версия | выход без установки | выход без установки |
| Установлена более новая версия | отказ понижать версию | отказ понижать версию |
| Приложение ещё запущено | требование закрыть | требование закрыть |
| Нужны права администратора | не нужны | обязательны, иначе `1603` |

Приложение живёт в трее, поэтому закрытое окно не значит остановленный
процесс: замена запущенного приложения оставила бы старое в памяти, работающее
с файлами, которых на диске уже нет.

### Когда установка всё-таки упала

Windows сворачивает разные причины в один код, поэтому после неудачи скрипт
печатает расшифровку кода и оставляет полный лог установщика, печатая из него
блок вокруг `Return value 3` — там установщик пишет, что именно не смог.

Частые коды:

| Код | Что означает |
|-----|--------------|
| `1603` | установка не удалась; причина — в логе |
| `1618` | уже идёт другая установка |
| `1620` | повреждённый MSI |
| `1638` | установлена другая версия |
| `3010` | установлено, Windows просит перезагрузиться |

Лог лежит в `%TEMP%\quita-install-*.log` и переживает установку намеренно:
удалять его в `finally` означало бы показывать пользователю путь к файлу,
которого уже нет.

## Что и когда запускается

Три workflow, и они не дублируют друг друга:

| Workflow | Когда | Что делает |
|----------|-------|------------|
| `ci.yml` | пуш в `main`, любой PR | линт, тесты, аудит зависимостей |
| `release.yml` | пуш в `main` | версия, changelog, теги, автослияние |
| `build.yml` | вручную, из `release.yml` | установщики для четырёх платформ |

Два прогона на один пуш — это не дубли: один проверяет код, другой ведёт
версии. Объединять их в один файл можно, но тогда починка версионирования и
починка сборки окажутся в одном месте, а разносятся они чаще всего по
причинам, не связанным между собой.

**Установщики собираются не при каждом пуше.** `build.yml` запускается только
через `workflow_dispatch` из `release.yml`, и только когда Release Please
действительно создал релиз, то есть когда в `main` попал коммит с типом
`feat`, `fix`, `perf` или `refactor`. Правка README, документации или
пайплайна релиз не создаёт и сборку не запускает.

Задача `changes` в `ci.yml` решает, что именно проверять. Сборка под три
платформы занимает около пятнадцати минут, и запускать её из-за опечатки в
README незачем: за сорок коммитов в `main` ровно 17 были документацией
или правкой пайплайна.
Разделено так:

| Изменено | Что запускается |
|----------|-----------------|
| `src/`, `src-tauri/`, `scripts/`, `tests/`, `package.json`, `pnpm-lock.yaml` | всё, включая сборку под три платформы |
| Только `.md`, `docs/`, `.github/` | линт, тесты, аудит. Без сборки приложения |
| Только `.github/workflows/` | линт и тесты |

Проверки документации живут в Rust, а читают README и скриншоты, поэтому
правка текста всё равно запускает их — иначе оптимизация тихо отключила бы
ровно то, что изменилось.

### Откуда берутся прогоны, которые ничего не делают

| Состояние | Сколько было | Почему |
|-----------|--------------|--------|
| `action_required` | 11 | Release Please открывает свой PR токеном репозитория, а GitHub держит такой прогон до ручного одобрения. Никто не одобрял: 1.2.3 ждал этого кнопкой. Сейчас одобряет задача слияния, а сами задачи CI на такой ветке скипаются — версия и changelog не требуют сборки |
| `cancelled` | 9 | Новый пуш отменяет незаконченный прогон предыдущего. Это осознанно: прогон устаревшего кода бесполезен |
| `failure` | 5 | Настоящие поломки, все исправлены |

## Сторонние действия в пайплайнах

Все сторонние actions закреплены на SHA коммита, а не на тег:

```yaml
- uses: tauri-apps/tauri-action@84b9d35b5fc46c1e45415bdb6144030364f7ebc5 # v0
```

Тег — закладка, которую владелец репозитория может переставить на любой
коммит. Если злоумышленник получает доступ к аккаунту, поддерживающему
`pnpm/action-setup` или `tauri-apps/tauri-action`, переставленный тег
подставит его код во все пайплайны — с нашими токенами и секретами. SHA
недвижим: сдвинуть его не может никто, включая владельца.

Особенно это касается `tauri-apps/tauri-action`: он работает в задаче,
которая собирает установщики и получает `TAURI_SIGNING_PRIVATE_KEY`.
Ключ подписи держит автообновление у всех пользователей приложения —
это самая дорогая мишень во всём репозитории.

Чтобы закрепление не превратилось в вечное отставание, обновления приходят
автоматически: `.github/dependabot.yml` следит за экосистемой
`github-actions` и раз в неделю открывает pull request с новым SHA. Посмотреть
и слить — всё, что нужно от человека. Версия тега остаётся в комментарии
рядом с SHA, чтобы по тексту файла было видно, какая именно версия
используется.

## Секреты и права токена

### Что вообще хранится

Ровно один секрет: `TAURI_SIGNING_PRIVATE_KEY`. Это base64-строка minisign,
одна строка, без вложенного JSON — формат, который GitHub надёжно маскирует
в логах (структурированные данные в секретах маскировать нельзя, и официальное
руководство об этом предупреждает).

`build.yml` также ссылается на `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, но такого
секрета в репозитории **нет**, и подпись от этого не страдает: ключ подписывает
с пустым паролем, что проверено командой `tauri signer sign`. Ссылка оставлена
намеренно — если ключ когда-нибудь защитят паролем, подпись продолжит работать,
а не сломается молча.

**Ключ без пароля.** Это осознанный компромисс, а не недосмотр: пароль пришлось бы
хранить вторым секретом в том же репозитории, и взломанный репозиторий забрал бы
оба значения разом — защиты от этого пароль не добавляет, только добавляет
неудобство при ротации. Реальная защита здесь — доступ к аккаунту и к
`gh secret set`.

### Права `GITHUB_TOKEN` по пайплайнам

| Workflow | Права | Почему |
|----------|-------|--------|
| `ci.yml` | `contents: read` | Ничего не пишет |
| `build.yml` | `contents: write` | Публикует файлы релиза |
| `release.yml` | `contents: write`, `pull-requests: write`, `actions: write` | Создаёт релиз, PR, одобряет зависший прогон CI и запускает сборку |

У `main` включена защита ветки: обязательны все шесть задач CI, история должна
быть линейной, force-push и удаление ветки запрещены, и администраторы
подчиняются тому же правилу (`enforce_admins`). Из этого следует приём, на
котором держится выпуск: пропущенная задача отчитывается успехом, а workflow,
не попавший в прогон, не отчитывается никогда. Поэтому релизный PR запускается
пустым — версия и changelog не требуют сборки, а проверки от него всё равно
приходят.

`ci.yml` запускается и на pull request, а задача `rust` компилирует код из
этого PR — то есть выполняет чужой `build.rs`, пока держит токен. Права
`contents: read` на уровне workflow означают, что даже ветка, запушенная в сам
репозиторий, не получит токен на запись. Это соответствует рекомендации из
руководства GitHub: «good security practice to set the default permission for
the `GITHUB_TOKEN` to read access only for repository contents».

Токен нигде не подставляется прямо в `run:` — только через `env:` или через
вход действия. Это защита от инъекции в оболочку, о которой предупреждает то
же руководство.

| Проверка | Результат |
|----------|-----------|
| Ключи, `.env`, базы данных в истории git | Не было ни разу за всё время |

## Проверка зависимостей

`cargo audit` и `pnpm audit` запускаются в CI на каждом прогоне. Advisory
появляются со временем без единого изменения кода: `rustls 0.23.45` пролежал в
`Cargo.lock` с четырьмя advisory сквозь месяцы зелёных сборок, потому что
проверки в пайплайне просто не было.

Два предупреждения остаются незакрытыми, оба — сборочные зависимости без
исправления:

| Advisory | Крейт | Почему оставлено |
|----------|-------|------------------|
| `RUSTSEC-2024-0370` | `proc-macro-error` 1.0.4 | Крейт заброшен, приходит через `gtk`. В бинарь не попадает |
| `RUSTSEC-2024-0429` | `glib 0.18.5` | Некорректные `Iterator`-имплементации, приходит через `tauri`. Путь до этого кода приложение не использует |

Третье предупреждение — не advisory, а **yanked-версия**: `zip 4.6.1` помечена
на crates.io как yanked, и приходит через `tauri-plugin-updater`, который требует
`zip ^4`. Вся ветка 4.x помечена yanked, обновиться внутри неё некуда, а свежий
`tauri-plugin-updater 2.14.0` требует ту же ветку — проверено обновлением замка.
Пока плагин не перейдёт на новый major, предупреждение останется: `cargo audit`
считает yanked предупреждением, а не поломкой, и печатает его в логе прогона.

Проверка идёт обычной командой, а не сторонним действием, и это не вкусовщина.
`rustsec/audit-check` вдобавок публикует результат как check run через API, а
токен у `ci.yml` только на чтение — сознательно, потому что задача `rust`
компилирует код из pull request. В тот день, когда база advisory впервые
сообщила про yanked-версию, это действие уронило задачу с 403 на
`create-a-check-run`, хотя сам аудит не нашёл ничего: упало не про зависимости,
а про то, как о них сообщить. Команде права не нужны вовсе, и на pull request
из форка она работает тоже.

Обновлять транзитивную зависимость вручную не нужно: предупреждение сработает
в CI, если появится advisory. Но заглядывать в список стоит — снятый
`ignore` должен уйти вместе с обновлением крейта.

## Нотаризация macOS

Пока не настроена: приложение не подписано Developer ID и не нотарифицировано,
поэтому первый запуск на чужом Mac требует подтверждения в системных настройках.

Как только появится подпись, порядок сборки меняется: собрать `.app` → подписать
→ notarize → запечатать в `.dmg`. Именно тогда замена бинаря изнутри станет
невозможной и обновление должно идти только через проверку подписи.

Описание шагов и нужные секреты — в `.github/workflows/release.yml`, в секции
`tauri-action`.
